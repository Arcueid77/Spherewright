# Spherewright Agent playbook: opening and core operation

Read this playbook before the first gameplay action in a session. It is also the embedded MCP resource `spherewright://agent/playbooks/opening-movement-v1`, available without a live Bridge.

## Open a saved world without continuing old automation

This is the public MCP preparation method's default when `recoveryMode` is omitted. Continuing an old task requires an explicit execution/recovery mode; the legacy wire mode named `default` remains available only when chosen explicitly through MCP.

For ordinary opening after an absence, use `prepare_resume_owned_game` with `recoveryMode=open_saved_primary`. The complete exact owned primary and original durable Journal are checked independently of the old credential's expiry, quarantine or Journey deadline. This same-Native mode opens the world paused at its saved tick; it does not Resume, charge, fly, resave, replay an action or grant execution time. Old task outcomes, Journey accounting and deadlines stay intact. New automation needs separate applicable authority and fresh Native admission. Human gameplay controls remain available.

Require the `opensSavedWorldOnly`, `previousAutomationRemainsStopped` and `newChargingProhibited` echoes, evidence version1, exact candidate tick and confirmation digest. Applicable existing conversation authority for this exact disclosed read is sufficient; do not repeatedly ask the owner. Prepare itself takes no confirmation. A normal saved world does not expire: the new credential issued after this opening grants future saved-world access only, including weeks later. It grants no automatic execution; the previous continuation modes reject it.

Normally the primary must cover the known ticket progress and any same-owned fixed LastExit. If the owner explicitly accepts losing the exact unsaved interval, additionally pass `acceptUnstoredProgressLoss=true`, `minimumRecoveryGameTick` equal to that known floor and `expectedRecoveryGameTick` equal to the exact complete primary. Check `discardedUnstoredProgressGameTicks`. Source/floor changes require a new matching plan; no checkpoint/autosave fallback or ticket editing. Missing identity, Journal, same-Native evidence, durable consumption or Native completion still fails closed. Poll the unique action; completed means the archive opened with old automation stopped, not that a previous task recovered or a save occurred. Offline loader/Pause substitutes do not prove Unity execution.

This guide describes the 0.5.0 development interface for DSP `0.10.35.29151`, retaining the 0.4 protocol surface; source-specific offline and live evidence is recorded in [native compatibility validation](https://github.com/Arcueid77/Spherewright/blob/main/docs/validation/native-29151-preflight.md). Historical 29145 production acceptance remains fixed at `2a7a98d1932c404e3a7abc2c11233d9c0b8780d9`. Read the installed component versions and package manifests for their exact build identity, and [Releases](https://github.com/Arcueid77/Spherewright/releases) for published versions. Editing this guide does not update an installed MCP or frozen package. Capability, current authorization, native executability and final acceptance are separate. This guide grants no gameplay, loading, recovery, installation, deployment or publication authority.

## A new finite recovery authorization for a remote primary

When the owner separately authorizes a new bounded automatic recovery window, prepare `recoveryMode=authorize_remote_primary_recovery` at an idle menu. Supply its absolute `recoveryDeadlineUtc`, `recoveryScope=continue_original_finite_task` and finite natural-charge caps. This is a new explicit authorization after disclosure and exact digest confirmation. Ordinary opening, an old completed action, consumption or a generic instruction to continue does not supply a new wall-clock budget. It can use the protected file-access provenance after expiry or a saved-world-only opening, while the old continuation modes retain their original restrictions.

Without progress-loss acceptance, this entry uses the complete current primary or, only when that primary is older than the current credential, the fixed LastExit whose complete owned/same-version proof exactly equals that credential's minimum tick. A merely larger LastExit from another progress boundary is refused. Both complete files, the original Journal/flight witness, cumulative spending and return reserves remain bound through confirmation and Native admission. The disclosure names the selected source; no arbitrary save selection, old-action replay or tick refund is introduced. Explicitly accepted primary rollback retains its separate exact-loss rules.

For this explicit new-authorization entry only, matching immutable consumption/attempt replicas may recover saved-file identity when no newer active generation exists. This creates a fresh saved-world-only file-access credential, preserving the old consumed token, attempt, outcome and window unchanged. The exact current fixed LastExit, complete primary, same Native version and original Journal must agree; another progress boundary, missing/changed replicas, a pending resume or reuse of the already-derived generation refuses. This is not execution authority: fresh window disclosure, digest confirmation, cumulative-budget checks and full Native handoff still precede any new load. No consumed plan is replayed.

If the original tick allowance is exhausted, this same mode accepts a separately owner-approved `additionalVoyagerGameTicks` from0 through108000. Check the prepared addition and `originalJourneyMaximumGameTicks` / `effectiveJourneyMaximumGameTicks` before confirming its digest. The addition is measured above the immutable original cap and is not stacked with a previous proposal. All observed spent time stays charged; the original record, return ticks, fuel and warpers remain protected. The confirmed effective cap must fund Native initialization, movement, construction and the original-home return. A new wall deadline alone does not grant ticks.

This mode loads only the exact complete same-Native owned primary. It holds the original Journal, successful outbound checkpoint as a non-loadable witness, current Journey and any matching fixed LastExit. It never asserts an old action failed or completed, follows an old consumed action, or loads that checkpoint. Explicit progress loss uses the same exact floor/tick pair as ordinary opening. Discarded observed time stays charged against the original Journey: funding includes that debit during admission, and successful strict takeover persists it once as conservative spent time. Original maximum ticks, issued/deadline fields, return energy/core/warper floors and old outcomes remain intact.

Require `remotePrimaryRecoveryAuthorizationUsed`, evidence version2, the exact primary tick, discarded-tick count, `conservedObservedProgressDebitGameTicks`, proposed deadline/scope/caps and confirmation digest. The conserved debit includes previously discarded observed time retained through saved-world-only opening and normal shutdown; `discardedUnstoredProgressGameTicks` describes only the present load. The protected file-access credential retains this observation without granting automation or changing its physical save minimum. An older open-only credential missing the observation remains unknown and cannot authorize automatic recovery; ordinary file access remains available. A healthy normal-save credential clears the already-persisted observation to prevent charging it twice.

The Plugin must pass the existing exact loader, paused initialization, Native151/501 projection, contact, permitted natural charging and strict idle checks before healthy takeover and normal primary Save. Missing/changed proof, unknown observations, exhausted original reserves or debit persistence failure stops the attempt; preserve the original action and failure evidence. A successful offline Store/coordinator/contact fixture does not prove Unity or a real Save. This guide grants no execution window.

Before loading, compare the startup `Spherewright loaded module:` records for Plugin, Core, Contracts and Native against the candidate/Native module identities. They report loaded CLR MVID and informational version without reading disk paths or game state. A matching disk install alone does not prove the loaded cohort; these records alone do not prove Native health.

## Continue an existing return-only task from its current save

Use `prepare_resume_owned_game(recoveryMode=resume_return_only_task)` only for an already granted return-only task. Supply the current protected `resumeToken`, the exact fixed LastExit `expectedRecoveryGameTick`, and `recoveryScope=recover_and_return_only`. The complete source must equal the credential's current progress boundary; a larger tick from another branch is rejected. A later preservation receipt may establish an exact newer boundary only when it also matches the current primary's complete fingerprint and the same task/session/action. The original checkpoint is historical proof and is never loaded.

Omit `recoveryDeadlineUtc` to retain the effective original window; an exhausted window rejects before Load. A proposed new absolute UTC window, at most3600 seconds, requires separately applicable explicit owner authority and the disclosed digest confirmation at commit. `returnOnlyContinuation` discloses the original task ID, original tick cap, remaining ticks, original/effective deadlines and whether new wall authority is required; `newTicksGranted=false` and `newChargingProhibited=true` are mandatory. No charge caps, rollback or prior-action outcome assertions are accepted. Existing original Journey UTC, spent amount, items, energy and return reserves remain unchanged. Applicable standing authority within this exact scope needs no repeated conversation approval. Complete installation, menu verification and the full-save backup before starting the finite window. MCP checks the typed no-charge return-only echo even when a deadline is omitted; Native health remains unproved until the actual admission chain completes.

Commit consumes the current credential once and records a bounded continuation under the same original task. Native paused initialization, real contact and strict idle must finish before ordinary Save and a renewed healthy credential can complete recovery. Only the original-home return, stop and normal Save are permitted. Failure latches the first same-sample evidence and pauses; no rekeyed retry or automatic window renewal follows. Exact stable-pause preservation Save can retain progress and a proof-only receipt, without clearing quarantine, changing the failed result or issuing a Load/Resume credential. A consumed or unresolved authorization is still rejected. Offline Native substitutes are not runtime health or a completed return.

## Commit discipline

- For ordinary actions, prepare only the next approved action and require `prepared=true`, a fresh token, `commitAllowedNow=true` and no blockers. Read-only previews are a separate tokenless contract. Do not stockpile tokens or sweep candidates.
- Reauthorization prepares intentionally return `commitAllowedNow=false` with `USER_CONFIRMATION_REQUIRED`. When every other blocker is absent and the exact disclosed mode's explicit conversation requirement is satisfied, commit the same still-fresh plan with the confirmation flag and exact digest. Obtain a subsequent explicit reply where that mode requires it; only the documented active fixed-AutoSave0 mode can use an existing matching grant. Do not wait for another prepare to return true or fabricate a true preflight. This confirmation resolves only the disclosed confirmation requirement, never another blocker.
- Direct-Bridge scripts keep prepare/commit in the same protected caller context; do not print or persist a `planToken` to cross processes. Ordinary MCP prepare/commit tool calls may carry the plan normally. An orphaned plan can be discarded only after proving zero accepted/in-flight actions; possible acceptance means reconcile its original action.
- Use the correct hash domain. Research uses `expectedSelectionStateHash` from `selectionStateHash`, not the general progression `stateHash`. For configuration, sorter-filter uses root `configurationStateHash`; storage-capacity uses full `stateHash`. First inspect the actual payload/hash source before diagnosing staleness.
- Existing Lab callers such as `Invoke-SpherewrightNormalAction` must bind both commit `sessionId` and `planetId`. Do not hand-build a fresh commit payload. Two rejected commits at the same stage stop that caller for diagnosis; a malformed/lost response is not proven rejection.
- After every `spherewright_commit_*`, poll each returned original `actionId` with `spherewright_get_action_result` until `terminal=true`. A commit acceptance or host timeout is not completion. If a synchronous commit has no `actionId`, use its documented terminal result and fresh-read. Check terminal/succeeded, identity, actual IDs, materials/inc and reciprocal edges. Lost responses, observer errors, format assertions or timeout after possible acceptance freeze new writes; never change key and replay.
- For ordinary configure plans, `targetObjectId` is optional; returned binding is not a request-hash echo. Keep explicitly documented mode-specific checks. Sorter configuration has a request-bound `expectedStateHash`; `plannedSorterFilterItemId`/nullable target are not mandatory configuration fields and configuration terminal `targetObjectIds` may be empty. To independently verify it, reuse the current Core canonical hash if independently verifying it; do not invent echoes or replay an accepted action after a caller assertion fails.
- One game writer owns the current finite declaration. Handoff requires original writer stopped, no in-flight actions or unreconciled results and an explicit single-writer handoff. Retain complete protected intent/receipt coverage, including unmatched commit intentions.
- Retain `actionId` and its terminal result before formatting optional observations. Ordinary normal-action receipts may expire after the configured retention window measured from observed completion; active work, uncertain/recovery evidence and checkpoint-bound flights are protected from expiry. At retained-evidence capacity, new normal commits are refused before acceptance, never admitted by evicting evidence. A missing old receipt does not prove non-execution. Do not assume every DTO has `capturedAtGameTick` or invent fields. A reporting/script error is not an action failure; reconcile without replay. For Save, fresh-check `lastOwnedSaveGameTick`, `ownedSaveState`, `writeHealth` and protected-resume availability.
- Fix result, scope, successful prefix, request/time/write budget, completion and stop conditions before execution. New Lab audit windows default to 20 where configured; existing ten-write declarations keep their count/limit. Reserve required normal save within the same budget. At the limit freeze commits, independently reconcile/audit, then explicitly reopen. Two similar native failures retire the candidate family for structural redesign.
- A read-only result with `wholePlanExecutable=false` is not executable. Existing finite authority may cover separately approved necessary work, but each action still needs native preparation and the exact budget. It does not authorize unapproved recovery, another world or formal publication.
- Sampling keeps the original game-tick deadline, wall deadline and request cap. A later zero-production window does not prove no earlier production. Preserve failed windows/gaps, caller timing and original evidence; no automatic budget extension/restart or retrospective pass.

Direct inspection uses **objectId, not entityId** (positive built, negative prebuild); player reads use fresh localPlanetId, configure uses entityId, and transfer uses storageEntityId. An ID absent from the first100 entities while nextCursor exists is not proven missing. Correct schema errors and do not replay successful construction.

`attached_existing_save` with `historicalCoverageComplete=false` means an absent first event is not proof that the item was never made. Retain `mechaResearchItemBuffer`/`autoManageResearchItems` and before/after progression. Its **3600 points** per item are not extra package stacks. Normal management can return whole buffered items; never round up remainders. This is not permission to accept arbitrary inventory gains. Unexplained quantities/triggers/action boundaries stop new writes.

Capture `completionItemRewards` (at most32 entries) before research completion. It is not a delivery receipt: null/missing means unknown, empty list means observed no rewards. Preserve order/duplicates and reconcile `unlockTick`, full inventory/inc, buffers and capacity. Unknown delivery, capacity overflow or multiple possible sources leave the gain unresolved. Never replay a completed action. Rewards are not handcraft or production and must not create or backfill a first-production Journal event.

Read units: research-lab buffers are points/3600, ordinary stock items/1. Electrical `power-generation-current-tick` is never fuel inventory. Exclude this role even when an older Plugin incorrectly reports items/1; `unitsPerItem=0` means no conversion, never divide by zero. Its integer is capped; use full-width power summary for energy.

Native production is a rolling 600-tick window, not an interval ledger. Do not sum overlapping windows or apply complete-interval inequalities to gapped windows. Keep overlapping or gapped windows and inventory intervals explicit. A lower-bound inflow below target is inconclusive, not an upper-bound failure; zero `P=C` or full stock alone never proves sustainable supply. Preserve corrected criteria without retroactively passing old windows; fixed target/tolerance and gap-reset rules remain unchanged.

## Stalled Move recovery

- For `position_stalled`/`route_stalled` do not submit the same target again.
- Inspect nearby objects including belts and sorters/inserters. Retain every distinct object ID even when positions coincide. Use current catalog/inspection for item identity; rough radii are not horizontal walking footprints. Remember that incomplete or expired pagination cannot rule out obstacles. After escape stay outside the observed obstacle cluster; crossing the same obstruction is not a new route. Do not dismantle a working line without separate authority.
- One identified obstacle: tangent-project away from it and prepare one surface target about **5 m** away.
- Multiple/unknown obstacles: two orthogonal tangent axes, at most four targets `+u,-u,+v,-v` about **4 m** away, each direction **once**. Poll each to terminal, stop at first success; all four failures stop the search.
- The landing capsule is vegetation, not a guaranteed factory entity. Retain the fallback.
- When the original business now prepares, perform it rather than driving to its centre.

All recovery attempts use the existing `prepare_move`/`commit_move` flow. Never teleport, inject input, write position or add an unbounded pathfinder.

Prove both physical endpoint slots before marking the local step complete. Do not broadly skip connections, admit an unproved ID or run a zero-change assertion before accounting for the addition.
