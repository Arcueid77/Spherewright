# Spherewright Agent playbook: opening and core operation

Read this playbook before the first gameplay action in a session, especially after creating a new world. It is also available from the MCP resource `spherewright://agent/playbooks/opening-movement-v1`.

## Session entry and ownership

Version migration is not a default resume exception. The exact researched expired-primary pairs are `0.10.34.28529 → 0.10.35.29057`, `0.10.34.28529 → 0.10.35.29088`, and `0.10.35.29088 → 0.10.35.29104`; no other direct or chained jump is implied. `reauthorize_expired_primary` may prepare only the exact healthy expired primary after full source/Journal checks. Verify evidence version 2 and its `sourceGameVersion` / `targetGameVersion` disclosure before confirming. Never edit ticket expiry or relabel historical Journal versions. Adoption must preserve all entries and prior transitions, persist the new directional transition, normally resave, and read back the new native format before issuing a new credential. Verify Journal `originGameVersion`, `currentGameVersion`, `versionTransitions`, durable sequence and pending/error status. Unknown pairs, downgrades and ordinary cross-version default resume reject; consumed failures require reconciliation, not replay. Offline build/tests are not native-load validation.

1. Call `spherewright_get_status`, read this resource, then fresh-read the session and player before deciding what to do. Keep using the current session, planet, revision, and state hashes; never reuse a snapshot from before a load, restart, or player intervention.
2. At the idle main menu, honor the user's intent and use only an advertised protected resume path or the normal new-world flow. Never guess, enumerate, or pass a save name.
3. A world manually loaded by the player is restricted. The only adoption path is save-import prepare, showing its exact confirmation prompt, waiting for an explicit reply in a later user message, and then saving to an independent owned copy. Do not claim Journal history from before that boundary.
4. If writes are disabled, the world is unowned, or write health is not healthy, remain read-only until the documented ownership or recovery flow succeeds.
5. A Codex/MCP Host restart is not a game restart. Leave DSP running and follow the [running-game reconnect rules](#restart-and-interplanetary-flight); do not save, close, reload, clear the accepted count, or replay an unresolved action as Host cleanup.

## Expired planned-restart credential

`restartResumeAvailable` advertises stored provenance, not an unexpired loading capability. If a healthy planned-restart ticket expired, do not edit its expiry, renew it offline, select LastExit, or import a copy to pretend the original Journal continued. Use the existing resume prepare tool with `recoveryMode=reauthorize_expired_primary` and no confirmation/tick overrides. This narrowly previews the **exact ticket-bound primary at its saved tick**, with matching full embedded identity/version/peaceful state, full-file hash and the original Journal at exactly its durable checkpoint; a newer Journal or changed file rejects.

Show the returned candidate tick and `confirmationPrompt`, then wait for a **subsequent explicit user reply**. This mode intentionally returns `commitAllowedNow=false` with `USER_CONFIRMATION_REQUIRED`; it is not an executable approval yet. Only after that reply may the Agent call the existing resume commit with `userConfirmedInConversation=true` and the exact `confirmationDigest` from that same fresh plan. The digest is a protocol echo, **not a code the user must type**. Other blockers still prohibit commit. If the short plan expires or evidence changes, prepare and disclose again; never transplant approval to changed evidence or another token.

The Plugin rechecks provenance, original Journal, menu revision and the complete primary, holds read-only file leases through adoption, and persists an attempt record and consumed tombstone before native loading. Interrupted/failed attempts require manual reconciliation; no automatic retry or continuation of a pending attempt is implemented. After success, poll the unique action to terminal and verify same identity, saved/healthy status and Journal continuity. The action includes normal primary resave before success and a fresh restart ticket; preserve the accepted-write audit budget and never replay earlier construction. Offline tests are not live recovery evidence.

## Commit discipline

1. Fresh-read the session and player before prepare. Use the current session, planet, revision, and the hash required by that exact action. Check each prerequisite against the actual response field and name any failed field; never collapse local caller errors into a generic "gate failed" or claim a native rejection. For research selection, session ownership is `ownedBySpherewright` and the required request hash is `expectedSelectionStateHash` from fresh `selectionStateHash`, not the general progression `stateHash`.
2. Prepare only the next intended action and commit it promptly. Plans are short-lived; do not stockpile tokens or flood the server with candidate prepares. For a direct-Bridge short-lived script, keep its prepare result and matching commit in the same protected caller context; do not print or persist a `planToken` merely to cross a process boundary. Ordinary MCP prepare/commit tool calls may pass the returned plan through their normal protocol and do not need to share a shell process. If a direct-Bridge caller exits before commit and a fresh check proves zero accepted/in-flight actions, discard the orphaned plan and prepare afresh. If commit may have been accepted, reconcile its original action instead of replaying with a new key. On a stale-state rejection, fresh-read and prepare again. Require `prepared=true`, a fresh token, `commitAllowedNow=true`, and no blockers. For ordinary configure plans, `targetObjectId` is optional and `expectedStateHash` is the server's plan binding, not a request-hash echo. Use the correct inspected hash in the request; do not invent additional response-echo requirements. Keep explicitly documented mode-specific checks, such as storage-capacity's planned configuration.
   When operating locally through the direct Bridge, reuse the existing `Invoke-SpherewrightNormalAction` helper for supported ordinary actions: it fills both commit `sessionId` and `planetId`, uses one idempotency key, and polls the same action. Load the protected audited Bridge client after the ordinary action client when durable raw receipts are required. Do not hand-build a fresh commit payload for each routine action. Two rejected commits at the same stage require stopping for caller review, not trying a third guessed payload; a rejected commit is not an accepted game action.
3. Give each logical commit one UUID idempotency key. If the caller loses a response or times out, query the returned action when known or retry the exact same request with the same key. Never generate a new key to replay an uncertain mutation.
4. After every `spherewright_commit_*`, poll every returned `actionId` with `spherewright_get_action_result` until `terminal=true`. A commit acceptance or host timeout is not completion. If a synchronous commit returns no `actionId`, use its documented terminal result and then fresh-read.
5. If an outcome remains unknown or write health enters quarantine, stop all new writes. Reconcile only the retained exact action when the API offers a proof, otherwise use the protected owned-world restart path. Never repeat the original mutation speculatively.
6. After a successful Move, fresh-read the player. Continue ordinary business only after `movementState=Walk`, speed is at most about `0.1 m/s`, and core/fuel energy is adequate for the next leg. Move completion proves arrival distance, not dry land. If still in `Drift`, do not wait indefinitely while hover drains energy: one bounded normal Move back to a recently verified clear Walk waypoint may be used as shore recovery, with fresh sufficient energy, terminal polling and a new Walk/low-speed readback. An unknown shore is not permission for blind target sweeps, flight or position writes.

For a low-speed Drift whose public position fingerprint changes between requests, the existing Move tool supports explicit `allowPassiveDrift=true`. Fresh-read the player immediately before prepare and use that returned hash. The server permits only idle Drift at at most0.15m/s, no forge/construction/player order, unchanged capacity and all existing non-position PlayerAction fields, and at most0.05m drift within2 seconds of that same inspection. Check the returned `moveStateBinding` origin/hash/tick, limits and shortened expiry; prepare and commit must fit that original bound. Do not issue another player read before committing, because it invalidates this prepared binding. This option does not choose a waypoint or relax terrain, ownership, Native movement or actual Walk/low-speed/energy proof. Omit it for ordinary stationary Walk moves and all other actions; an expired or refused candidate still follows the bounded stop/replan rules.
7. Retain `actionId` and its terminal result before formatting optional observations. Ordinary normal-action receipts may expire after the configured retention window measured from observed completion; active work, uncertain/recovery evidence and checkpoint-bound flights are protected from expiry. If retained evidence reaches capacity, new normal commits are refused before acceptance, not admitted by evicting evidence. A missing old receipt is never proof that its action did not execute. Do not assume all DTOs have `capturedAtGameTick` or invent response fields. A reporting/script error after commit is not an action failure; reconcile fresh state without replay. For Save, verify the fresh session's `lastOwnedSaveGameTick`, `ownedSaveState`, `writeHealth`, and protected-resume availability.

For an ordinary transfer's terminal result, first require `terminal=true`, `succeeded=true` and the exact action/item/storage identity. `beforeTargetAmount/afterTargetAmount` are the storage counts; the matching `itemDeltas` entry is the player's change. Missing fields are unknown, not invented zeros; no successful proof or unexplained flow still requires reconciliation. A finite diagnostic seed is not a sustained-supply baseline.

## Rear pickup on mixed-input belts

When available, `beltCargo.rearPickup` identifies the **aligned native pickup packet** only for the selected segment at the end of an open path. Its `state=observed` gives one packet's item/count/inc at the stated tick; this is separate from the segment's item-sorted aggregate, which is **not queue order**. `no_aligned_packet` does not mean an empty belt. `not_applicable` means a non-tail segment or closed path; unavailable/missing/null is unknown. Do not use these states as proof of a clear input or sustained throughput.

For a station, fresh-read the reciprocal belt input, configured item capacities and `needs`. The current native input cannot skip an aligned packet whose item is not needed; a full configured slot can therefore obstruct another item on a mixed input. Establish repeated packet/needs evidence before claiming sustained blockage. Input `storageIndex` records the last received slot, not an input filter. Prefer separate justified input routes for independently backpressured items. Any capacity increase is a finite drain until sustained supply is demonstrated; never clear stock to manufacture throughput, replay a partial route, or infer an automatic repair from this read-only observation.

## Research buffers and inventory accounting

- For `attached_existing_save` with `historicalCoverageComplete=false`, an absent first-event entry is **not proof that the item was never made**. Historical counters seed the detector without invented timestamps; later crafting or production of a seeded item legitimately leaves the Journal unchanged. Prove the action from its successful terminal and material readback. Never replay a completed craft or backfill pre-tracking history to satisfy a caller assertion. An incomplete history is not a persistence failure.

- Capture `get_progression_state.technologies[].completionItemRewards` before selecting research or observing its completion. It is a complete native prototype list of `itemId`, `name`, `count` (at most32 entries), **not a delivery receipt**: null/missing means unknown; an empty list means observed no rewards. Malformed, mismatched, oversized or unresolved item metadata returns null, never a partial list. Preserve order and duplicate entries. Older Plugins may omit this field.
- A normal technology completion can grant backpack items. Reconcile its actual `unlockTick` with retained before/after full inventory (including inc), mecha research buffers, capacity and original action terminals. Separate a later reward from an earlier successful transfer. Metadata alone does not prove successful delivery; capacity overflow, unknown metadata or multiple possible sources leave the gain unresolved and require stopping new writes. **Never replay a completed action**, allow arbitrary positive deltas, or change state hashes to pass an audit. A reward is **not handcraft or production** and must not create or backfill a first-production Journal event. This read-only list grants no ability to add items or complete research.

- Native production is a rolling **600-game-tick window**, not an interval ledger. Do not sum overlapping windows or apply full-interval `production >= consumption` to gapped windows: periodic production/consumption phases can show a sampled deficit on a conserved line. Keep coverage gaps and the separate inventory observation interval explicit. A conservative inflow lower bound below a target is **inconclusive, not an upper-bound failure**. Preserve failed experiments and declare corrected criteria before a new run, without retroactively passing old windows. ## Energy and approach

- Before a long move, harvest, construction batch, or flight, check core energy, the fuel chamber, usable inventory fuel, and the intended charging route. Refuel only with the native refuel prepare/commit pair, or move once to a known safe point inside a powered charging network and wait for fresh energy growth. Do not keep probing a blocked path until the core is empty.
- When advertised, recipe catalog items expose `acceptedAsMechaFuel`, `fuelHeatValueJoules` and `fuelType`. Fuel is not limited to named fuel rods; use actual native acceptance, not names or remembered IDs. Null means unknown, and item heat does not prove burn rate or travel range. Acquire and refuel the actual native one-stack amount with conservation readback. If a recovery read already shows stable Walk, cancel the recovery intention; a nearly empty core is not sufficient merely because prepare permits a target. If Drift alone makes preparation stale, at most three immediate fresh-read/prepare attempts may be composed without model delays, but retry only requests known not to have been accepted and never replay a commit outcome.
- `prepare_move` validates a finite target, not path clearance. `prepare_harvest` also does not prove that its automatic approach corridor is clear. ## Stalled Move recovery

- If the terminal result says `failureKind=position_stalled` or `failureKind=route_stalled`, **do not submit the same target again**. Fresh-read before every new candidate.
- Inspect nearby factory objects **including belts and sorters/inserters**, not just large buildings. Use the current catalog/inspection for item identity instead of remembered IDs. After a successful short escape, stay outside the observed obstacle cluster before turning toward the destination; changing a far endpoint while crossing the same obstruction is not a new route. Do not dismantle a working line to clear a path without separate authority.
- If one nearby obstacle is identifiable, project the direction from the obstacle toward the player onto the player's local spherical tangent plane. Prepare/commit one target about **5 m** along that away direction, reprojected to the planet surface.
- If several obstacles are nearby, or the landing capsule/base cannot be identified reliably, form two orthogonal axes on the local tangent plane. Try at most the four targets `+u`, `-u`, `+v`, `-v`, each about **4 m** away and each direction **once**. Poll each attempt to terminal and stop at the first success. If all four fail, stop and inspect again; do not expand into unbounded search.
- A landing capsule is a DSP vegetation (`VegeData`) collision object, not a factory entity. It may be visible through the vegetation resource API, but callers must keep the four-direction fallback because its identity/name is not a general factory-entity guarantee.
- Move is only an approach primitive. If the original business action (for example harvest, transfer, or build) now prepares successfully, perform that bounded business action instead of continuing to drive toward the building or resource center.

All recovery attempts use the existing `prepare_move` / `commit_move` flow. Never teleport, write player position, inject input, replay a failed target, or run an unbounded pathfinder inside the Plugin.
