# Safety model

The explicit elevated2001 source-cover subset binds one empty independent raised tail, its exact source ID/hash/native start position and a free destination. The full old cargo path must be open, unfed and empty before preparation and native revalidation. Every native point remains either the exact non-removing zero-cost source cover or an occupancy/material-checked NEW point; no arbitrary trimming, destination reuse or automatic routing is allowed. Creation proves the exact reciprocal source-to-prebuild link. Completion proves ordered old-plus-new empty membership and the old members' native position/geometry/edge preservation, allowing only the prior free source output to change. Ordinary free elevated spans and other source-cover modes retain their separate boundaries.

Researched directional native migration pairs are exactly `0.10.34.28529 → 0.10.35.29057`, `0.10.34.28529 → 0.10.35.29088`, `0.10.35.29088 → 0.10.35.29104`, and `0.10.35.29104 → 0.10.35.29131`. Expired-primary reauthorization may disclose these pairs; the separate active-credential `reauthorize_version_changed_primary` mode only discloses the last pair. All migration loads require subsequent explicit confirmation of the prepared disclosure. The exact `28529 → 29088 → 29104 → 29131` Journal chain is bounded to three durable transitions; skipped links, fourth transitions and other direct/chained jumps reject. Ticket, primary and Journal effective source version must agree and the host must be the researched target. Historical Journal origin and earlier entries/transitions remain unchanged; only the new transition may append after adoption. The original Journal lease releases only for that durable append while the primary lease and pending checkpoint still block saving/gameplay; persistence failure rejects adoption. Normal save reads back exact identity, native v7/v13/patch23/GameDesc10 tuple, current version and tick before signing a target-version credential. Unknown/mixed tuples, downgrade, replay and default cross-version resume remain forbidden. The exact active-credential29104-to29131 same-primary migration was subsequently confirmed and live-verified with a normal resave, all102 Journal entries, three transitions and the complete6492-entity saved factory preserved (R1222-R1223). This narrow result does not validate another candidate, expired-primary variant or future transition; see [migration evidence](https://github.com/AvaloNero/Spherewright-Lab/blob/14478a03c64c550e644c559405c8496b647552e7/releases/v0.4.0/evidence/2026-10-12/native-primary-29131-preparation-r1218.md).

Expired healthy planned-restart provenance may only enter the explicit `reauthorize_expired_primary` prepare/commit flow. It is never an active resume capability: the exact ticket-bound primary must match its saved tick, complete embedded identity, current version and peaceful mode; both protected ticket replicas and the original Journal must agree. Prepare binds complete file/Journal evidence and menu revision to a short plan, discloses its scope, and requires subsequent conversation consent plus a plan-specific digest echo. Commit revalidates all evidence, holds the primary and Journal read-only through adoption, and writes protected attempt evidence plus a durable consumed tombstone before loading. No expiry edits, LastExit fallback, arbitrary names, copied world or fabricated history are allowed. A crash/failure after consumption is fenced for manual reconciliation, not automatically retried. Only normal saving after successful identity and Journal adoption issues a fresh ticket. This implementation does not claim live validation merely from unit tests.

An unchanged, still-active healthy credential may disclose only its exact primary for29104→29131 via `reauthorize_version_changed_primary`, evidence5. It does not become a default resume or fixed-AutoSave0 credential. Prepare forbids confirmation/tick overrides and does not consume or load; it returns the exact recorded candidate plus versioned prompt/digest. Commit requires a subsequent explicit reply, mode-specific active provenance, both replicas, original Journal, menu revision and full primary evidence, then durable consumption before loading. Expired/same-version/unknown pairs and changed/reused evidence reject. Credential dates, owned identity and past Journal history are never rewritten to qualify.

- `AllowWrites` defaults to `false`; every write is prepare + idempotent commit + readback.
- Factory/save reads and ordinary gameplay writes require a session created or explicitly adopted by the current Spherewright process. An unrelated session exposes only its opaque restricted session ID, revision, and import availability—not save, player, planet, or factory content.
- New worlds are peaceful, 1x resources, sandbox-disabled, and created through DSP's new-game path. Unrelated saves are never enumerated or actively loaded. A player-loaded current world can cross the boundary only through an exact-session prepare, a separate subsequent confirmation in the Agent conversation, and a normally saved new owned copy; the original is never addressed by the import API. The other post-M0 named-load addition is a Spherewright-created pre-flight checkpoint addressed internally through its protected reusable ticket.
- `combatModeStatus` and `sandboxModeStatus` remain explicit runtime evidence. A missing descriptor or non-peaceful world fails closed; sandbox state and resource multiplier do not gate commits and never expand the bounded action surface.
- Computer Use, screenshots-as-state, visual recognition, and keyboard/mouse macros are forbidden for gameplay execution and acceptance.
- No action may grant items, inject storage/buffers/energy, write technology progress, directly complete prebuilds, teleport the player, change game speed, or edit a save. Calling DSP's normal save API for the exact current process-owned identity, an internally generated pre-flight checkpoint, or an explicitly confirmed player-loaded world's new internal copy is allowed; enumerating, opening, accepting, overwriting, renaming, or deleting the original save is not.
- Refuelling must move already-owned native fuel and prove count plus proliferator-point conservation. Research-result acknowledgement uses the native UI fade/close lifecycle and never changes research state directly.
- Logistics-station fleet transfer may move only already-owned item `5001`/`5002` between the player package and the matching idle fleet counter. It binds idle and working craft plus prefab capacity, rejects proliferated deposits and collectors, and must preserve cargo slots, energy, warpers, configuration, the other fleet, working craft, the player hand, and unrelated package items. It never creates a drone/vessel or writes station cargo.
- Normal actions must prove the same costs the game imposes: range, inventory, capacity, energy, recipe/technology unlock, construction, power, and elapsed game ticks.
- A move or harvest that continuously has no core energy, reactor energy, current reactor item, or usable fuel for 600 game ticks is terminated as a proven `action_failed`; Spherewright aborts only its exact owned player order and never injects recovery energy or fuel.
- A powered move is also terminated as `action_failed` when it accumulates less than 0.75 metres of physical displacement for 180 game ticks, or when 600 game ticks of continued motion fail to reduce the best remaining target distance by at least 1 metre. These checks stop the exact owned order before the global timeout; they do not classify a fully power-starved grace window as a collision.
- `prepare_move` validates a fresh finite surface target but does not claim path-collision prediction. A stall result explicitly says not to retry the same target and gives bounded 5 m single-obstacle / four-by-4 m orthogonal recovery guidance. Every candidate remains a separate audited prepare/commit Move; the Plugin performs no unbounded automatic search, teleport, direct position write, or injected input.
- Move's default hash check is unchanged. Explicit `allowPassiveDrift` uses only the latest server-recorded external inspection, for an idle, alive/on-planet Drift player at at most0.15m/s. Prepare and commit bind the same original PlayerAction hash with the trusted origin position substituted, require unchanged exact core capacity and other existing hashed state, and enforce at most0.05m total displacement within2 monotonic seconds; they never renew the baseline. Forge/construction/current or other active player orders exclude this mode. A subsequent external player read invalidates the prepared binding. The disclosed `moveStateBinding` is part of the plan hash; Native surface/energy/order/stall checks and post-arrival dry Walk proof still apply. It cannot admit a fabricated inspection hash, another action kind or a water landing.
- DSP exposes one current player order. Move and harvest actions therefore use single-flight at commit time: while either is non-terminal, a second player-order commit returns retryable `SERVER_BUSY` instead of replacing the first order and leaving two misleading action records.
- All current DSP/Unity reads and writes are dispatched to Unity's main thread. Pipe workers see only immutable DTOs.
- Plans bind the bridge/session/planet, action type, exact target identity, parameters, before-state hash, and resource budget.
- The 0.4 scope permits bounded native blueprint construction and per-entity native upgrades, not unconstrained multi-object writes. The current blueprint tools are strictly data inspection/export (`executable=false`), restricted to explicit code or selected current-owned entities with bounded decompression/object counts and an explicit unsupported-content rejection. Metadata is untrusted. No file picker or blueprint executor is implied.
- The executable upgrade subset is ordinary manufacturing assemblers plus basic sorter2011→2012 only. It calls native `DoUpgradeObject`, never writes `protoId`, consumes a complete higher-tier item and refunds the old item into reserved package space. It binds revision and fresh identity/configuration/filter, checks live cargo, reciprocal links and native timing/power immediately, and quarantines any uncertain cost/result instead of replaying. A sorter needs both actual factory links matching its pick/insert targets, not merely a valid subset of existing edges or positive cached target IDs. Assemblers reset processing progress; basic sorters rescale the retained cycle fraction. Belts, advanced stacking sorters and other upgrade families are not enabled.
- Any future finite blueprint executor must expose partial per-object outcomes, preserve normal materials/drones/time, and cap per-frame work. Cancellation stops unexecuted work only. Restart requires durable owned-bound evidence reconciliation and fresh tokens; it must not replay a full partially completed module or claim a transactional rollback.
- Save-import prepare binds the exact unowned process/session/revision/`GameData` without reading or exposing world content. Its plan remains non-committable until a later user message explicitly confirms the returned disclosure; commit requires the caller to declare that confirmation and both original-save/journal boundaries, then revalidates peaceful mode, records the actual sandbox/resource settings, and requires local-factory readiness before its sole normal-save attempt. Sandbox and resource multiplier do not gate import. A true save return without exact header proof quarantines import for that loaded session; only result lookup is allowed until the player intentionally reloads the original into a new session.
- Factory observations expose a complete mutable `stateHash` and a stable `endpointStateHash`. Logistics builds bind the latter so identity, pose, and existing connections remain exact while ordinary production progress and buffers may advance; belt input/output slots are treated as explicit physical endpoints when extending a path.
- The v0.4 diagnostic bundle is composed only from deep-copied public Overseer DTOs captured in one Unity-main-thread work item. It rejects any cross-domain factory/tick mismatch, uses a versioned public allowlist schema, and has no field for save identity, filesystem paths, auth credentials, or action plan credentials.
- Before creating a sorter prebuild, completion attribution snapshots older same-item entities at the prepared source pose. Those IDs cannot satisfy the new action's readback, because DSP legitimately anchors multiple sorters at an identical building-side position.
- Commit results are cached by `(sessionId, idempotencyKey)` across Pipe reconnects. Each session has its own configured capacity, entries expire after `IdempotencyRetentionMinutes`, same-key retries replay during that window, and different requests conflict.
- If a mutation started but the result cannot be proved as before or expected-after, the session write subsystem is quarantined.
- Quarantine can be cleared in-process only by a two-stage proof for the exact retained outcome-unknown build: conserved item cost, unique new entities/components, and complete directed topology must all match, and reconciliation never repeats the original mutation. If that proof is unavailable, the only continuation path is a new session loaded from fixed `LastExit` through a protected, expiring, one-time ticket that binds the exact owned identity, source shutdown, minimum tick, planet, peaceful state, and the per-save journal's last durable checkpoint. Newly issued tickets record journal identity, tracking boundary, and minimum durable sequence. Resume validates that protected file both before load and after adoption; a missing, recreated, truncated, or identity-mismatched journal leaves the loaded world restricted, preserves the ticket for repair/retry, and blocks automatic save and gameplay writes. Legacy tickets without this extension remain load-compatible and are upgraded by the next healthy save. Sandbox/resource settings are preserved and reported but do not gate adoption.
- Explicit newer-LastExit recovery is a separate opt-in to the existing protected resume, not a forged quarantine or automatic fallback. It requires actual conversation confirmation, a valid healthy Journal-bearing ticket, exact approved candidate tick and known progress floor, bounded embedded identity/version/peaceful validation and unchanged full-file evidence. Commit holds a read-only file lease through adoption; older/drifting/unsupported sources reject. Candidate tick must survive adoption, Journal confirmation and normal primary resave. No arbitrary path, directory scan, autosave selection or offline primary overwrite is allowed.
- A flight checkpoint is persisted and header-verified before native launch. Reload requires its protected token and a persisted recovery-required/interrupted-flight lifecycle, cannot accept a save name, and adopts the payload only after the internal slot, exact tick, embedded primary owned identity, origin planet, and peaceful state match. Sandbox/resource settings are preserved and reported but do not gate adoption. Failure may repeat this same load; success removes the capability immediately, a covering primary save retires it, a newer exact primary header supersedes legacy state, and every ticket has a 24-hour expiry.
- The Pipe authentication token, absolute private paths, raw save identity/content, private game objects, and stack traces are never returned through MCP or written to normal logs. Opaque plan, one-time resume, and reusable checkpoint tokens are returned only in their intended authenticated DTO fields and are excluded from ordinary logs and committed evidence.
- The Named Pipe uses a per-process random name, startup-rotated token, and ACL restricted to the current Windows SID.
- The old sandbox basic-line experiment is excluded from M0 Plugin compilation and the public write surface.
