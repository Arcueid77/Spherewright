# Bridge protocol

Protocol version: `1`.

Primary reauthorization evidence is **version 2**: the prepared plan also binds and echoes `sourceGameVersion` and `targetGameVersion`; a version-1 reauthorization echo is rejected. Only same-version or the researched direct `0.10.34.28529 → 0.10.35.29057` or `0.10.34.28529 → 0.10.35.29088` pair (not `29057 → 29088`) is supported. Journal snapshots expose immutable `originGameVersion`, effective `currentGameVersion`, and `versionTransitions` separately from first-occurrence entries. A transition is persisted only after native adoption and exact old-Journal validation, before continuity confirmation allows primary resave/new credential issuance. Default resume retains exact current-ticket version matching.

The existing `prepare_resume_owned_game` also accepts `recoveryMode=reauthorize_expired_primary`. No new tool or arbitrary save selector is added. Unlike `verified_newer_lastexit`, this prepare forbids confirmation and caller tick overrides: it previews only an expired, unconsumed, healthy ticket's exact primary and original Journal. It returns `candidateGameTick`, `recoveryEvidenceVersion=2`, `exactEmbeddedIdentityVerified=true`, `userConfirmationRequired=true`, `confirmationPrompt`, and a plan-bound `confirmationDigest`; `commitAllowedNow=false` includes `USER_CONFIRMATION_REQUIRED`. After showing that disclosure and receiving a later explicit reply, commit sends `userConfirmedInConversation=true` and the same `confirmationDigest`. These are an Agent attestation and protocol echo, not a user-entered authorization code. Default/LastExit commits leave these fields false/empty. A mismatched Plugin echo suppresses the plan token; changed evidence/revision, consumed or conflicting replicas, a missing/changed Journal, or an unconfirmed commit refuses loading. The attempt record and tombstone are durable before native load; interrupted attempts are fenced for manual reconciliation, not replayed. See the [playbook](agent-playbook.md#expired-planned-restart-credential) for the exact workflow and evidence limits.

`reauthorize_expired_autosave0` is a separate explicit mode of the same tools, with evidence version3 and its own disclosure; primary reauthorization retains version2. It resolves only native `GameSave.AutoSave0`; no source-name or slot parameter exists. Prepare forbids confirmation and requires `minimumRecoveryGameTick` and `expectedRecoveryGameTick`. The exact same-identity peaceful candidate must cover that known progress floor, be strictly newer than the ticket and any observed primary, and have the same supported source/runtime version (no migration). Its tick, full-file lease fingerprint, request bounds, mode/source, revision and expired-ticket/Journal provenance bind the plan. Commit requires subsequent conversation confirmation and its exact digest, rechecks all evidence and durably consumes provenance before loading. No fallback to primary, LastExit or other autosaves is permitted. Original Journal continuity and candidate-tick adoption precede normal saving under the original owned primary name and a new restart credential. Offline policy/coordinator tests do not prove actual Unity loading or post-load entity persistence.

Each message is a four-byte little-endian signed length followed by UTF-8 JSON. Negative lengths and lengths over 1 MiB are rejected before allocation. A zero-length frame is accepted by the frame layer and rejected by the JSON layer.

The first message on every Pipe connection must be an authenticated `handshake` carrying the active `bridgeInstanceId` and startup token from the current-user-only runtime descriptor. Any pre-authentication request or invalid credential closes the connection.

## Current public MCP surface

`get_build_catalog.buildings[].fuelPowerProfile` is an optional, bounded native base-rating record for ordinary thermal/fusion generators only (2204/2211). `generationEnergyPerTick` and `fuelEnergyUsePerTick` are positive 64-bit joules per game tick; `fuelTypeMask` copies the native fuel mask. Missing/null is unknown or unsupported, not zero or free power. Invalid/nonpositive/over-bound scalars and non-ordinary generator types are not partially advertised. These prototype values are neither live generation nor fuel stock/delivery; native load, fuel and proliferation still determine actual operation. No new tool, action, hash version or Foundry planned-generation credit is introduced. ### Detail-only belt cargo observation (0.4 development slice)

`spherewright_inspect_factory_entity` can inspect the current local factory or an explicitly requested, already-created, identity-verified simulation-resident factory on the current owned star, even when its display is unloaded. It rejects other stars, unavailable simulation pools and inconsistent pool identities; it never creates/loads a remote factory. The same read-only route adds nullable `beltCargo` on exact completed belts from either allowed factory. `beltCargo` is separate from `buffers`, not populated in paginated lists, and not part of existing `stateHash`, `configurationStateHash` or `endpointStateHash`; those action semantics and versions are unchanged. A material cut is still one selected factory only. Station details and the optional cut carry their own game-tick stamps; callers must require matching stamps before joining them. This is a synchronous main-thread observation, not a cross-call transaction, write token or preservation proof.

`state=observed` gives `capturedAtGameTick`, native path/segment identity and bounds, `pathClosed`, `cargoStackCount`, `itemCount` and item-sorted `items` (item/count/native inc and stack count). Coverage is `unique_stacks_touching_selected_belt_segment`: a stack crossing a segment edge can appear in both adjacent reads, so the results must not be summed into path inventory. Empty counts prove only this selected segment was empty at that tick, not zero flow, a stalled belt, or an empty entire path.

An explicitly selected material cut also accepts identity-verified stations and ordinary thermal/fusion generators. Station item stock is the same-tick `logisticsStation.storageSlots.count/inc`, excluding orders and fleet cargo; buffered generator fuel is `fuelPowerState.bufferedFuelCount/inc`. Residual `loadedFuelEnergyJoules` remains energy, never extra items. Generator electrical buffers retain their existing J/t semantics and are excluded from item-stock sums. Unsupported generators, missing fuel/slot observations, unit mismatch or incomplete native identities make the cut unavailable. Selection/path bounds and all action hashes remain unchanged.

The adapter copies at most530 bytes (512 selected cells plus9 guards per side), checks the native ten-cell representation and zero-based cargo IDs, and confirms each distinct reference via bounded `CargoPath.GetCargoAtIndex` before copying item/stack/inc scalars. It neither scans the whole path/container nor traverses other factories. Null/missing means not observed; `state=unavailable` returns a fixed `reasonCode`, null totals and no partial items. Oversized/out-of-range segments, unresolved seam fragments, malformed/ambiguous cargo references, absent pool identity or failed native readback never become successful zero counts. Current native component and owned-world checks remain in force. Belt upgrades still require a separate full affected-path/chunk/cargo proof and are not enabled by this observation.

Optional `beltCargo.rearPickup` observes only `coverage=open_path_rear_pickup_aligned_packet`. It uses the same bounded copied window and same-tick native cargo readback, with no pickup/removal calls. Only a segment ending exactly at an open path's rear is applicable. `state=observed` returns `capturedAtGameTick`, `markerPathCell`, `itemId`, `name`, `count`, `inc` for the single aligned packet. `no_aligned_packet` is not an empty segment or zero flow; `not_applicable` explicitly distinguishes closed paths/non-tail segments; unavailable or missing is unknown, with no invented item/count. Segment `items` is item-sorted, not queue order. A fresh reciprocal station input and needs/capacity plus repeated observations are needed to diagnose sustained head-of-line blockage; this snapshot alone proves neither dispatch nor repaired supply. The additive field does not change action hashes, writes, tool count or upgrade capability.

### Governor proposal (0.4 development slice)

Factory observations retain component and pagination boundaries: `list_assemblers` is not an all-producer/consumer query. Matrix production is in `componentKind=lab`, with research mode and matrix-point units handled separately. Complete the relevant immutable filtered pages and actual bounded directed connections before declaring absence. The current entity reader does not capture `CargoPath` cargo into belt `buffers`; an empty list means **unobserved**, not verified empty. Diagnose transport using reciprocal endpoints, observed sorter/device buffers and native production windows. Do not clear storage or construct a duplicate consumer based on a partial trace.

`sourceStateHash` uses `governor-source-v2`: stable selected identity/pose/reciprocal endpoints, recipe, native acceleration mode, sorter filter/targets, storage settings and power-network identity. It deliberately excludes live buffers, cargo/proliferation, processing progress, inserter carrying/stage and instantaneous power ratio. Those remain measured evidence/stock deltas and blocker inputs. The earlier development binding used the volatile configuration hash and could reset every normal production window; it is not valid evidence of production instability. `FactoryEntitySnapshot.forceAccelerationMode` is copied from native assemblers. Endpoint hashes now also bind this mode and sorter filter, so changing either invalidates an old explicit blueprint selection without making ordinary cargo movements stale. Old process tokens/hashes are never reused after cold deployment.

`spherewright_get_governor_plan` is read-only: `phase=governor_proposal`, `executable=false`, `balanced=false`. Select 1–32 exact current-owned local entities with fresh endpoint hashes/recipe IDs, target item/rate, tolerance (0–0.5, exclusive zero), and a 36000–216000 game-tick validation window. Optional external supply and recipe choices reuse the Foundry compiler. This proposal is not a write plan, approval token, automatic expansion loop or completed acceptance result.

Measurements reuse the same-tick Overseer local-planet item counters; they are **not per-selected-machine production counters**. The proposal checks whether the selection contains all direct target producers. Baseline metadata is bounded to eight selection series per session and three independent native windows of the explicitly fixed `measurementGameTicks` (600/default or3600); overlapping reads cannot manufacture independent evidence. New session, changed actual source, observed item scope or measurement period, regressed game time or sampling gaps invalidate the old baseline; windows predating the new binding do not qualify. Measurement binding `governor-measurement-binding-v3` includes the selection series, static source hash, canonical observed item IDs and measurement period, not the proposed rate or machine budget. Thus, before locking, the caller may request exactly twice a ready measured rate without erasing unchanged-source observations. The complete Foundry scale/cost and Governor proposal are still recompiled and rehashed: fresh-check and lock the **new** ready proposal before any expansion/write. An unstable baseline remains unstable, and already locked target/tolerance/scale cannot be changed. Three stable nonzero windows only establish a candidate baseline, not ten-minute post-expansion success.

`supply` separates full target-chain demand, actual production/consumption, nonnegative local production surplus, additional demand/supply shortfall, and selected-buffer stock/deltas with their own observation interval. Consumption is a lower bound under starvation; local surplus excludes imports, reservations and transport. Production minus consumption is **not** an inventory delta. Power/logistics summaries, bounded findings and reciprocal-link blockers retain their evidence scope.

Alternatives compare supported native upgrades (whole target device cost and old-device refund), additional Foundry machine capacity, and an explicitly selected copyable module. Costs/power labelled as machine-only exclude unplanned logistics and generating infrastructure. Predicted nameplate gains never become measured gains; `actualTargetGainPerMinute` remains unknown. Preserve the pre-execution baseline, target, tolerance and window outside subsequent proposals; use fresh normal prepare/commit for the selected finite work and then separately prove at least ten game minutes. The current proposal tool does not yet persist or certify that acceptance window.

#### Governor explicit parallel-construction comparison

Governor optionally accepts `parallelExpansionBlueprint`, using the same explicit `FoundryBlueprintRequest` (code, native site and free boundary ports). Before a stable nonzero baseline with a positive increment, it returns no full comparison and explicitly reports that the layout is unassessed. Otherwise `parallelExpansion` contains the existing Foundry plan and its reusable construction `intent`, at **target minus measured baseline**. Its rate basis is `target_minus_measured_nonzero_baseline_v1`; no caller can supply historical rates. Same-capture session/planet/tick/revision, exact code hash/position/rotation/player-bound site assessment, original material graph, complete construction hash and native power capture are checked together. The optional envelope uses the existing 256KiB code/site limits and at most33 ports, with the stricter Foundry shape checks still applied.

`alternatives[].costScope` distinguishes `machines_only`, `whole_upgrade_devices`, `selected_module_objects` and `all_explicit_module_objects_external_infrastructure_excluded`. A full parallel comparison includes every explicit building, logistics and power object, native placement/full inventory/technology, full-base-load power and rated channel budgets. Unplanned external supply/sink infrastructure is not priced or credited. `bounded_construction_ready_at_capture` means the existing construction plan can be freshly prepared; blockers produce `bounded_construction_blocked` plus `parallel_construction_not_ready`, never an executable/balanced claim or actual gain. The proposal fingerprint is `governor-proposal-v3`, with an additional `governor-parallel-proposal-v1` binding when applicable. No new tool, executor, approval store or gameplay write is added. Use the identical explicit layout, returned intent and construction hash with the existing prepare/commit flow; post-expansion observation omits the layout and keeps the previously locked declaration. Restart still requires fresh finite-build reconciliation. Only the durably locked Governor declaration can survive a covering protected planned resume; all passive observation credit is discarded.

#### Foundry native transport budget

`construction.transportBudget` describes rated full-power, single-item, no-backpressure capacity, not measured production. The native catalog exposes nullable `beltSpeedRaw`, `inserterSttRaw` and `inserterGrade`; unknown values never become free capacity. Every internal and boundary belt traverses its capacity edge in the bounded flow allocation. Basic2011/2012 sorter capacity includes the translated preview's native span;2013 stacking capacity is explicitly unavailable to this composition, without changing the ordinary blueprint allowlist. Shared allocated routes count once each against each channel. `allocatedRatePerMinute` may be below the requested demand when the graph is blocked: always check `internalFlowsRouted`, `canPrepare` and blockers, not the budget alone. `transportCapacityVerified` stays false in planning reads. Rated inputs, allocations and availability are hashed into the immutable plan; continuation rechecks current catalog rules and cannot reuse a stale material/transport contract. It still needs automatic boundary supply/sinks, full power and live sustained-throughput evidence.

#### Governor pre-execution throughput declaration

Private checkpoint v3 hashes decimal numeric values using invariant canonical text, so equivalent representations such as `31` and `31.0` survive the exact Plugin JSON serializer. Before publishing a durable lock the store validates the serialized-and-deserialized archive. Legacy v1/v2 records retain their original hashes: compatibility checks at most three alternate representations caused solely by Newtonsoft adding `.0` to whole-number baseline/target decimals. Values, identity, lock tick and all other metadata must still match; no archive editing, replacement baseline or credited historical windows are accepted.

`measurementGameTicks` defaults to600 and only additionally accepts3600. The latter reads the current local factory's native level1 automatic counters (`total[1]`/`total[8]`), validates their two bounded600-bucket rings, and declares the actual interval ending at `capturedAtGameTick - capturedAtGameTick % 6`. The partial last six-tick bucket is excluded, not invented. Normal Overseer tools and same-capture diagnostic findings retain their existing600-tick basis; only this Governor's actual production/consumption rates use the declared longer interval. It does not infer continuous instantaneous health from averages. Changing period discards candidate history; a locked declaration cannot change it. New durable checkpoints use version2 and include the period in integrity binding; version1 without this field retains its original hash and600-tick meaning. A new MCP refuses an old Plugin's nonmatching period echo. No new tool or gameplay write is added.

`get_governor_plan` optionally accepts `validationBaselineProposalHash`, never caller-provided baseline rates/history. A ready, healthy, attributable proposal with no unresolved `targetChainFindings` can be retained as one latest candidate per existing bounded source series (`validationBaselineAvailable=true`). These findings come from the target item diagnostic, a selected object or a path containing a selected object; all bounded planet findings remain visible, and `unattributedPlanetFindingCount` explicitly preserves the remainder without inventing a route to the selected line. Truncation still blocks; absence of attributed findings is not automatic upstream-supply proof. The first request using its exact hash must occur before any accepted write/source change, at the same revision, within3600 game ticks, with output still matching the baseline. It locks copied baseline/target/tolerance/duration/recipe-scale scalars. At most8 locked declarations exist per owned identity, in a bounded64KiB current-user-protected archive; no silent eviction, replacement or new write token is added. The lock is published only after a flushed atomic replacement succeeds (`declarationDurable=true`); storage failure returns an error and discards the candidate. The archive includes only server-captured immutable declaration scalars with an integrity checksum, never client-supplied history, samples, save names or tokens. The checksum detects corruption; filesystem ACLs establish trust. A new session may restore the same hash only for the same registered owned identity/game version after a healthy planned restart with confirmed Journal continuity. The consumed ticket's original minimum tick must cover the lock; a later current tick or automatic resave cannot repair a pre-lock load. Missing/corrupt/conflicting storage, legacy or quarantine/checkpoint recovery, and wrong/future save evidence do not restore it. All continuous observation credit starts at zero after restore; `durable=false` continues to describe samples, separately from `declarationDurable`. The selected source may legitimately expand after locking, but the measurement streak then waits for windows wholly after that new configuration.

`throughputValidation` records contiguous game-tick coverage from native rolling windows of the locked600/3600-tick period. Overlap is counted only once; duplicates and wall-clock time do not add duration. A one-tick uncovered gap starts a new streak. Zero/out-of-tolerance production, unavailable native windows, sampled power/diagnostic/attribution/write-health failure and tick regression clear observed progress without changing the declaration. Changed target, tolerance, duration, measurement period, item/planet/session or recipe scale rejects. Thirty-six thousand covered ticks prove the requested ten-game-minute window; `doubleThroughputTargetObserved` additionally requires an exactly2× target and tolerance<=10%. This is a bounded passive observer, not a build or expansion loop. `balanced` remains false: sampled health is not continuous tick-level health proof, and resource conservation, upstream automatic supply, transport, save/resume and complete-version gates remain separate. The observer was deployed in the617-test development cohort; its first live lock rejected unattributed global depleted-mine findings. The scoped correction has separate offline evidence and requires new same-session live validation after deployment.

Foundry and blueprint site previews optionally expose `power`, a separately hashed one-capture assessment. The read-only adapter copies bounded native network-node coordinates and reserves every existing consumer's max(work,idle,current) and charger demand, current exports, planned unproliferated machine/sorter demand and existing unpowered consumers picked up by new nodes. Core uses native maximum connection radii (not their sum), conservative projected coverage and planned-node component joins; ambiguous disconnected covers or near-boundary geometry are explicit blockers. Only new native wind generation is credited. Limits:32 planned objects,512 existing nodes,256 networks,8192 active consumer scan and2048 unassigned consumers. `fullBaseLoadBudgetSatisfied` is current capacity/coverage evidence only, not fuel sustainability, an executable plan or a write capability. Its hash includes the captured tick and is deliberately separate from construction assessment hashes; power sampling cannot make an otherwise unchanged native build plan stale every tick. Unknown capture returns `state=unavailable`, never presumed zero demand. Native build conditions and post-construction power/throughput inspection remain authoritative.

### Blueprint data and native upgrades (0.4 development slices)

Ordinary `prepare_build` sorter selection also preserves the native candidate-selection guard that precedes `CheckBuildConditions`: exact straight endpoint poses must face each other (maximum angular error below14 degrees for two devices, below11 when touching a belt). This bounded adapter does not reproduce native bent/offset searches. `TooSkew` candidates are rejected before native preview initialization; current endpoint IDs are revalidated before pool access. No existing object is moved or repaired automatically. Blueprint site objects additionally expose nullable `inputEndpointFacingDot/outputEndpointFacingDot`: a negative value means that connected device slot faces away from the other sorter endpoint; belt/open ends report null. These are diagnostics, not permission to clear `ErrorInserterData` or bypass any native condition. A historically working sorter is not necessarily a valid blueprint seed.

The finite subset also accepts ordinary unstacked storage2101. Current native parameters are exactly110 integers: banned-grid count, mode0/9, eight reserved zeros, then100 grid filters. The bounded reader rejects unknown/ignored settings; the Plugin verifies native capacity, bans, unused filter tail and valid stackable item IDs before native parameter application. `FactoryEntitySnapshot.storageConfiguration` exposes actual `gridCount`, `bannedGridCount`, mode and ordered `gridFilterItemIds` (bounded100, null if unavailable). It is not build-catalog's physical connection `slotCount`. Factory, endpoint and configuration hashes bind this optional tagged configuration, leaving non-storage encoding unchanged. Export rejects stack links and proves configuration roundtrip; completed-object reconciliation proves current native capacity/bans/mode/all filters. It deliberately ignores subsequent normal cargo movement: no cargo is serialized or copied. New storage still costs one complete item and uses the ordinary prebuild/drone path; no direct configuration or inventory writes are added.

`FactoryBufferSnapshot` adds `countUnit` and `unitsPerItem` without changing existing raw `count/inc`. Ordinary buffers use `items`/1; lab `research-matrix` buffers use `research_matrix_points`/3600. They represent research-point equivalents, not raw items available for transfer or complete technology budgets.

`inspect_blueprint` accepts an explicit `blueprintCode`; `export_blueprint` accepts `entities:[{objectId,expectedEndpointStateHash,expectedRecipeId}]` in the current owned local planet. Both require `sessionId/planetId`. Export uses only positive completed IDs, at most 64, within 64 m of the first selected entity. It never scans or writes files. Native `GenerateBlueprintData` and `ToBase64String` produce the code; source connections to unselected entities are returned separately in `sourceBoundaryConnections`, not silently treated as copied links. Cargo is never copied.

Input is bounded before native import: 256 KiB UTF-8 code, 128 KiB compressed, 1 MiB decompressed, 64 objects, 8 areas, 256-grid drag/area dimensions, 128 parameters per object. Only header0/1, payload2/patch1 and building marker -102 are supported. Native MD5F signature and byte-exact native import/export roundtrip must pass. The supported data subset is smelter2302, manufacturing assemblers2303–2305 (default or boolean acceleration mode), belts2001–2003 without labels, sorters2011–2013 (native span1–3/filter), Tesla tower2201 and wind turbine2203. Other types, settings, content strings, terrain reform, malformed references, unsupported versions or excess data explicitly reject the whole inspection. Titles/descriptions are returned under `untrusted*` fields and are never instructions.

The result remains **`phase=blueprint_inspection`, `executable=false`**. It includes supported poses/configurations, native indices/slots, boundaries, unlock flags and package-only aggregate `constructionItems`. Optional `site:{position,quarterTurns,expectedPlayerStateHash,stateHashVersion}` adds a read-only native site assessment with its own hash: at most32 objects, 64m radius, closed internal sorter ends and acyclic belt dependencies. Whole budget, native blueprint capacity, item/recipe/filter unlocks, range, terrain/tropic, collisions, occupied entities/prebuilds and every native condition must pass. No covers, implicit external matching, upgrades or demolition are permitted in this path. `nativeBlueprintObjectLimit` reports actual history capacity. The assessment issues no token and never commits on its own.

`prepare_blueprint_build` binds either explicit code/site plus its assessment hash, or one exact owned `resumeBuildId` plus its fresh progress hash (never replacement code/site). Both require fresh player hash and `maximumObjectsToSubmit`1..32. It reuses normal session/revision/GameData binding, short-lived tokens and UUID idempotency. `commit_blueprint_build` returns actionId/buildId. A local bounded executor submits at most one dependency-ready native prebuild per game tick, then waits for normal drones. Aggregate action results include `blueprintBuildId/blueprintBuildPhase/blueprintObjects`; each object tracks not_submitted, submitting, pending_construction, completed, blocked or outcome_unknown, exact inventory before/after hashes and IDs/ticks. This is not atomic whole-plan success. The action pauses successfully at its batch limit; phase `completed` requires all objects proved.

Progress is stored atomically under a current-user protected, exact-owned-identity path (32 plans/4MiB), never a save picker. Write-ahead evidence is flushed before each native create; exact one-item debit and prebuild/configuration/reciprocal proof follow it. A crash in that gap is unknown, not retryable. `get_blueprint_builds` without buildId returns summaries only, no fresh stateHash. Exact buildId reads reconcile immutable configuration, known entity/prebuild identity, all connections including free ends and non-regressing game tick; newly observed completion metadata must persist before exposure. Restart restores evidence, not tokens/authority. Fresh prepare continues only unsubmitted objects; whole-module replay is forbidden. Active finite construction excludes competing normal actions. Unknown results quarantine writes.

`prepare_cancel_blueprint` uses buildId and fresh exact progress hash; commit remains bound to the same build/action while natural construction may advance. `commit_cancel_blueprint` stops future submissions only, retains every existing prebuild/entity, and never auto-demolishes/refunds/claims rollback. ## Request rules

Configuration hash domains are mode-specific: `sorter-filter` requires root `configurationStateHash` in `expectedFactoryStateHash`, whereas `storage-capacity` requires full `stateHash`. A sorter request that can be positively identified as the current full hash returns non-retryable `INVALID_REQUEST`; an unmatched older/wrong-domain value remains `STALE_STATE` because its origin cannot be proved. Missing native configuration evidence fails closed. Inspect the actual request field before retrying; no canonical hash, prepare/commit binding or native mutation semantics are relaxed by this diagnosis.

`inspect_factory_entity` requires `objectId`, positive for a built entity and negative for a prebuild. Zero/missing and `Int32.MinValue` return `INVALID_REQUEST` after the owned-world guard; this is not evidence of a missing building. Do not reuse the `entityId` key from configure/transfer request schemas. Direct Bridge deserialization can otherwise default an unrecognized/missing ID to zero; older Plugins reported that case as `INVALID_ENTITY`. A nonzero representable ID still passes through the native existence check. The direct inspection read accepts only the local planet or an already-created, identity-verified simulation-resident factory proven to belong to the current local star. Native factoryLoaded is display state; reading does not set it or create/load a factory. Every normal-action prepare/commit remains local-planet-only; remote factory inspection does not widen construction or configuration scope. `get_player_state` still uses `planetId` from the fresh session's `localPlanetId`. An unfinished paginated list cannot establish that an object disappeared.

`inspect_factory_entity` additionally returns optional detail-only `sorterEndpoints`. An `observed/native_slots` result contains at most16 world-space positions and outward unit directions, slot index and current occupancy/neighbor; an `observed/belt_virtual` result contains four orientations with slot=-1 and null occupancy/neighbor. The latter does not identify a free physical slot. Null/unavailable means unknown, not no endpoints; malformed or over-limit input yields no partial poses. Lists and prebuild details omit this extension. Existing action/configuration/endpoint hashes are unchanged, and the read never creates a plan: use fresh prepare/commit and final reciprocal readback, and verify power/delivery separately.

Every save/player/factory request carries the active `sessionId`; planet-bound requests also carry `planetId`. Save import is the narrow exception that accepts only an unowned session's restricted ID/revision and exposes no world content before confirmation. A mutable prepare binds the current complete target/resource state and returns an opaque short-lived plan. Commit carries the plan token and a UUID idempotency key. Factory observations expose both `stateHash` for complete mutable device state and `endpointStateHash` for build connections. Build source/destination requests use `endpointStateHash`, which binds identity, pose, and existing connections without becoming stale solely because a miner, belt, or assembler advances normal production.

Ordinary sorter construction records any pre-existing same-item entities at the prepared source pose before calling DSP's native prebuild path. Completion excludes those IDs before topology verification, so two legal sorters that share the same building-side position cannot cause the newer action to be attributed to the older sorter.

New-game creation and exact owned-game resume are the ordinary main-menu mutations and have no active session/planet envelope yet. Flight-checkpoint reload may replace only the exact matching active owned game or run from an idle main menu; it can interrupt no active normal action except its own bound flight. New-game creation generates the save name and fixes peaceful mode, sandbox disabled, and resource multiplier 1x. Neither recovery path can enumerate or accept a save name. The primary-save resume fallback is internal-only, requires that exact protected ticket identity and a fresh file timestamp, and intentionally restores no post-ticket unsaved action.

A stale session returns `STALE_SESSION`, an unowned session returns `SESSION_NOT_OWNED`, and a stale target/resource snapshot returns `STALE_STATE`. Missing descriptor or confirmed combat mode blocks gameplay commits; sandbox state and resource multiplier remain visible evidence but do not block them.

Responses never contain the Pipe name, bridge authentication token, descriptor path, stack trace, absolute game path, raw save identity/content, or raw game component. Opaque plan tokens plus one-time resume/reusable checkpoint tokens appear only in their intended authenticated structured fields and must not be copied into logs or evidence documents. List methods are bounded and use session/planet/snapshot/filter-bound cursors.

## Action semantics

All normal-game mutations use separate `prepare_*` and `commit_*` methods. Prepare is read-only even when writes are disabled. Commit is single-flight by `(sessionId, idempotencyKey)`, rereads all preconditions on the Unity main thread, and records a queryable action state.

If a commit may have been accepted but its result is unavailable, the MCP mapping returns `ACTION_OUTCOME_UNKNOWN`; clients must retry with the same request/key or query `get_action_result`. They must never use a new key to guess-replay the action.

`prepare_move` validates the current owned session, planet, fresh player hash, finite surface target and arrival tolerance. It deliberately does not predict the collision-free path. A terminal movement stall now returns `failureKind` (`position_stalled` after the 180-tick displacement window or `route_stalled` after the 600-tick target-progress window), `stalledGameTicks`, `remainingDistance`, `doNotRetrySameTarget`, `recommendedRecovery`, `recommendedShortMoveDistanceMeters`, `orthogonalProbeDistanceMeters`, and `maximumOrthogonalProbeAttempts`. The coordinator still aborts only the exact `OrderNode` reference that it owns. It does not teleport, write position, or run an internal pathfinder.

`allowPassiveDrift` is an optional, default-false Move-only concurrency mode for a slow drifting player. It requires the hash from the latest external `get_player_state`; the server retains exactly one immutable eligible inspection. Inspect, prepare and commit require alive/on-planet `Drift`, finite positive core energy, unchanged exact core capacity, speed at most0.15m/s, empty forge, idle construction and no current player order. Prepare also rejects other active player-order actions. Both prepare and commit compare the original `PlayerAction` hash with only its position supplied from that trusted inspection, while independently enforcing a total displacement at most0.05m and a monotonic age at most2 seconds from the original inspection. Internal reads never refresh either limit; a later external player read invalidates an already prepared binding. `moveStateBinding` discloses the origin, original hash/tick, limits and deadline, is bound into the plan hash, and shortens the advertised expiry. All other existing PlayerAction fields remain bound, including its existing positive/nonpositive energy semantics; this is not full Player DTO equality. Default Move and every other action retain their existing exact fingerprint comparison. Water/terrain evidence, Native movement rules, single-flight/idempotency and terminal/Walk readback requirements remain unchanged.

An additive optional `surfacePreview` describes downward samples along the explicitly requested shortest surface arc, not route clearance. A span up to32m uses at most33 points, nominal spacing at most1m, and at most66 native raycasts on the owned world's main thread. It reports capture tick, arc length, query count, copied positions/hit elevations, unknown/risk counts, `state=observed|partial|unavailable` and `shoreRisk=detected|not_detected|unknown`. Hit booleans indicate validated copied hit evidence. Missing hits or inconsistent distances remain unknown; detected risk takes precedence over unknown samples. Long/invalid spans return unavailable rather than silently sampling a shorter route. Old servers and non-Move plans may omit the field. This advisory output changes neither the existing movement hash nor commit admission: small intervening features, obstacles, the actual controller route and later scene changes remain unproven. Arrival still requires a fresh Walk/low-speed/energy check; if already settled, discard an obsolete shore-recovery intention rather than committing it.
